# 启动与会话切换性能排查

检查时间：2026-09-16。用户反馈：电脑浏览器和 Android 均卡顿。

本次仅诊断，没有修改运行逻辑、数据库配置或部署。检查了当前工作区、线上公开主脚本、生产 SQL 聚合指标及生产日志的聚合统计。生产消息正文、账号标识和凭证未导出。

## 结论与处理顺序

1. **启动自动下载完整 Trace 是最大的已确认数据开销。** `/api/runs` 成功响应的中位体积为 14.10 MB，最大 17.90 MB；首页启动即请求最近 50 次运行，返回完整 events，而非列表摘要。优先移出聊天首屏；调试列表返回摘要，打开某次运行时再取详情。
2. **登录校验同步写 SQLite 已实际发生锁等待。** 生产数据库为 `journal_mode=delete`；会话校验在每个请求中更新 `last_used_at`，读取和更新均有慢查询与锁错误。优先对访问时间写入节流、在单次请求内复用身份解析，并单独验证 WAL、连接池及后台事务的并发策略。
3. **公开主脚本未压缩。** 一次 GET 实测下载 915,905 字节，耗时 1.916 秒。相同文件本地 gzip 后为 194,549 字节，减少 78.8%。应配置 JS/CSS/JSON 压缩，再做资源拆分和缓存。Android 使用包内资源，网络下载主脚本的成本主要影响 Web；两端都受大型脚本解析和初始化影响。
4. **会话全量加载和折叠内容提前渲染会放大长会话成本。** API 不分页，前端构建所有历史消息和折叠的思考时间线，再整体设置 `innerHTML`。优先加载最近一页，展开思考过程时再渲染明细。此项已确认代码路径，但尚未测得手机真实设备上的主线程耗时，不把它当作已经量化的 CPU 主因。

### SQLite 锁竞争证据

对最近 16,000 行 Gateway 日志中的慢 SQL，按代码位置聚合：

| 位置 | 慢查询样本数 | 慢查询样本中位数 | 最大值 | 锁错误次数 |
| --- | ---: | ---: | ---: | ---: |
| `internal/handlers/account.go:301`，session 查询 | 73 | 1,036.4 ms | 5,009.234 ms | 2 |
| `internal/handlers/account.go:304`，更新时间 | 46 | 635.1 ms | 5,015.217 ms | 5 |

这里的中位数只代表已被记录为慢查询的样本，不代表所有 session 查询。Connect 后台 worker 和 Pulse 写入也出现在慢 SQL 记录中。当前 DB 初始化设置 `_busy_timeout=5000`，与多个约 5 秒等待相符；需要后续关联具体事务，确定各次等待的锁持有者。

生产现有 386 个会话、1,978 条消息。`assistant.db` 约 345.33 MB；消息字段总量中完整 trace 约 281.51 MB、trace_summary 约 9.00 MB、正文约 3.69 MB。采样时系统 1/5/15 分钟 load average 约 0.11/0.13/0.20。这不支持把持续 CPU 饱和当作当时的主要解释，但不能排除间歇性负载。

## 代码链路

- `web/static/js/app.js:9698`：`refreshAll()` 同时启动 11 类加载，包含 Trace、工具、Drive、Pulse、Todo 等。
- `web/static/js/app.js:8251`：`loadRuns()` 请求 `/api/runs?limit=50` 并立即 `renderRuns()`。
- `agent/main.py:762`、`agent/trace/store.py:285`：run 列表直接返回完整 `RunRecord`，未裁剪 events。
- `web/static/js/app.js:12957`：渲染列表后继续 `renderRunDetail()`，未判断调试页面是否可见。本地首页实查：没有聊天消息时，隐藏 Trace 视图已含 626 个 DOM 节点。
- `web/static/js/app.js:9720`：已有登录态的启动路径调用 `void refreshAll()`，并不等待所有数据才能启用输入。因此主要问题是后台大请求抢占带宽、解析与渲染，而非这一启动分支直接 await 全部数据。
- `web/static/js/app.js:3216` 附近：账号切换/登录路径仍 `await refreshAll()` 后才隐藏登录层；慢 Pulse、Trace 等会延长这个路径。
- `gateway/internal/handlers/account.go:295`：`accountSessionUserID()` 每次成功解析均同步更新 session。
- `gateway/internal/database/db.go:26` 附近：连接配置只设 5 秒 busy timeout；生产实查日志模式是 `delete`。
- `gateway/internal/handlers/conversation.go:178`：消息查询没有 `LIMIT`。默认已经省略完整 `trace_events`，不应把完整 Trace 重复传输误归到普通会话详情接口。
- `web/static/js/app.js:14906`、`:15034`：加载会话后生成全部消息 HTML；命中缓存也会整体重新设置 `innerHTML`，并重新请求完整会话。缓存限制 20 个会话，没有字节上限。
- `web/static/js/app.js:15287`：思考过程即使折叠，仍构建时间线和内部 HTML。
- `web/static/js/app.js:15895`：每 5 秒轮询 `/api/tasks`，空闲且页面可见时也继续请求；响应中位数约 115 KB。可改为存在活动任务时快轮询、空闲时降频。

## 建议验收方式

第一批：聊天首屏不请求完整 run 列表，调试列表使用摘要；给 session 活跃时间写入节流并验证读写并发；为文本资源和 JSON 启用正确压缩。应补充首屏请求行为、列表/详情契约、登录态正确性、并发访问和节流边界的单元测试，先跑局部，再跑 `./scripts/test.sh`。

第二批：会话分页、折叠思考明细按需渲染、限制缓存字节数、取消已过时的切换请求、后台轮询自适应。使用同一账号及短/长/工具密集会话，在电脑和真实 Android 上分别测冷启动、首次切换、缓存切换；记录点击到正文可见耗时、主线程长任务、下载字节数和服务端锁等待。

本次诊断运行现有 startup、conversation pager、thinking process 三组 Web 单元测试，共 29 项通过。没有新增 feature 或修复，未运行全量测试；这些测试只能验证既有行为基线，不代表性能问题已修复。
